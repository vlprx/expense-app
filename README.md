# Expense App

RESTful API для управління користувачами, категоріями та витратами з використанням Flask і PostgreSQL. Застосунок підтримує автентифікацію за допомогою JWT, рольову модель контролю доступу RBAC та автоматизоване тестування.

## Використані технології

- Python 3.13
- Flask 3.1.3
- PostgreSQL 16
- Flask-SQLAlchemy
- SQLAlchemy ORM
- Flask-Migrate
- Alembic
- Marshmallow
- Flask-JWT-Extended
- Passlib
- Argon2
- Pytest
- Freezegun
- Docker
- Docker Compose
- GitHub Actions

- Bruno

Перед запуском необхідно встановити:

## Запуск застосунку

Клонуйте репозиторій:

```bash
git clone https://github.com/vlprx/expense-app.git
cd expense-app
```

Зберіть Docker-образи та запустіть контейнери:

```bash
docker compose up --build -d
```

Перевірте стан контейнерів:

```bash
docker compose ps
```

Застосуйте міграції бази даних:

```bash
docker compose exec web flask --app run.py db upgrade
```

Після запуску API доступне за адресою:

```text
http://localhost:5000
```

PostgreSQL використовує такі параметри підключення:

- Database: `expense_db`
- User: `expense_user`
- Password: `expense_password`
- Port: `5432`

Рядок підключення задається через змінну середовища `DATABASE_URL`.

## Моделі бази даних

Застосунок використовує такі ORM-моделі.

### User

Представляє користувача системи.

Поля:

- `id` — ідентифікатор користувача.
- `name` — ім'я користувача.
- `password_hash` — хеш пароля.
- `role` — роль користувача (`user`, `auditor`, `admin`).

### Category

Представляє категорію витрат.

Поля:

- `id` — ідентифікатор категорії.
- `name` — назва категорії.
- `user_id` — ідентифікатор власника категорії. Значення `NULL` означає глобальну категорію.

### Account

Представляє фінансовий рахунок користувача.

Поля:

- `id` — ідентифікатор рахунку.
- `user_id` — ідентифікатор власника рахунку.
- `balance` — поточний баланс.

Для кожного користувача автоматично створюється один рахунок із початковим балансом `0.00`.

### Record

Представляє запис про витрату.

Поля:

- `id` — ідентифікатор запису.
- `user_id` — ідентифікатор користувача.
- `category_id` — ідентифікатор категорії.
- `created_at` — дата та час створення запису.
- `amount` — сума витрати.

Між моделями налаштовані зв'язки, зовнішні ключі та каскадне видалення пов'язаних записів.

## Міграції бази даних

Для керування змінами структури бази даних використовується Alembic через Flask-Migrate.

Створення нової міграції:

```bash
flask --app run.py db migrate -m "Migration description"
```

Застосування міграцій:

```bash
flask --app run.py db upgrade
```

Перегляд поточної версії міграції:

```bash
flask --app run.py db current
```

Історія міграцій зберігається в директорії `migrations/versions/`.

## Автентифікація та авторизація (JWT)

Для автентифікації користувачів використовується JSON Web Token (JWT).

Реалізовано такі механізми:

- реєстрація користувачів;
- вхід до системи;
- перевірка пароля;
- генерація access token;
- перевірка токена під час виконання захищених запитів.

Паролі не зберігаються у відкритому вигляді. Для їх хешування використовується Argon2id.

### Реєстрація

`POST /register`

Приклад запиту:

```json
{
  "name": "Valeriia",
  "password": "SecurePass123!"
}
```

Під час успішної реєстрації створюється користувач із роллю `user` та автоматично створюється його рахунок.

### Вхід

`POST /login`

Приклад запиту:

```json
{
  "name": "Valeriia",
  "password": "SecurePass123!"
}
```

У відповіді повертається access token, який необхідно використовувати для доступу до захищених маршрутів.

Заголовок авторизації:

```text
Authorization: Bearer <access_token>
```

## Рольова модель контролю доступу (RBAC)

У застосунку реалізовано три ролі.

### User

Звичайний користувач може:

- переглядати власний профіль;
- переглядати власний рахунок;
- переглядати власні категорії та глобальні категорії;
- створювати власні категорії;
- поповнювати власний рахунок;
- створювати власні записи про витрати;
- переглядати та видаляти власні записи.

Користувач не має доступу до адміністративних операцій та даних інших користувачів.

### Auditor

Аудитор має права лише на читання.

Може:

- переглядати список користувачів;
- переглядати профілі користувачів;
- переглядати рахунки;
- переглядати категорії;
- переглядати записи про витрати.

Не може створювати, змінювати або видаляти дані.

### Admin

Адміністратор має повний доступ до адміністративних операцій.

Може:

- переглядати всіх користувачів;
- переглядати дані будь-якого користувача;
- створювати та видаляти глобальні категорії;
- створювати персональні категорії;
- змінювати ролі користувачів;
- створювати та видаляти записи;
- видаляти користувачів та пов'язані з ними дані.

Для захисту ресурсів застосовуються такі HTTP-статуси:

- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — недостатньо прав доступу.
- `404 Not Found` — ресурс не знайдено або він недоступний користувачу.
- `400 Bad Request` — некоректні вхідні дані.

## REST API

### Перевірка стану застосунку

| Метод | Маршрут | Опис |
|---|---|---|
| GET | `/healthz/live` | Перевірка працездатності застосунку |
| GET | `/healthz/ready` | Перевірка підключення до PostgreSQL |

Ці маршрути доступні без авторизації.

### Автентифікація

| Метод | Маршрут | Опис |
|---|---|---|
| POST | `/register` | Реєстрація користувача |
| POST | `/login` | Вхід та отримання JWT |

### Користувачі

| Метод | Маршрут | Опис |
|---|---|---|
| GET | `/users` | Отримання списку користувачів |
| GET | `/user/{user_id}` | Отримання профілю користувача |
| DELETE | `/user/{user_id}` | Видалення користувача |
| PATCH | `/user/{user_id}/role` | Зміна ролі користувача |

### Категорії

| Метод | Маршрут | Опис |
|---|---|---|
| GET | `/category` | Отримання категорій |
| POST | `/category` | Створення персональної категорії |
| POST | `/category/global` | Створення глобальної категорії |
| DELETE | `/category/{category_id}` | Видалення категорії |

### Рахунки

| Метод | Маршрут | Опис |
|---|---|---|
| GET | `/account/{user_id}` | Отримання рахунку користувача |
| POST | `/account/{user_id}/deposit` | Поповнення рахунку |

Приклад запиту на поповнення:

```json
{
  "amount": "200.00"
}
```

### Витрати

| Метод | Маршрут | Опис |
|---|---|---|
| POST | `/record` | Створення запису про витрату |
| GET | `/record/{record_id}` | Отримання окремого запису |
| GET | `/record?user_id=1` | Фільтрація за користувачем |
| GET | `/record?category_id=1` | Фільтрація за категорією |
| DELETE | `/record/{record_id}` | Видалення запису |

Приклад створення витрати:

```json
{
  "user_id": 1,
  "category_id": 1,
  "amount": "25.50"
}
```

Для всіх захищених маршрутів, крім реєстрації, входу та health endpoints, необхідно передавати JWT.

## Валідація даних

Для перевірки вхідних JSON-даних використовується Marshmallow.

Перевіряються:

- обов'язкові поля;
- типи даних;
- допустима довжина текстових значень;
- додатне значення суми;
- наявність користувача та категорії.

У разі некоректних даних API повертає HTTP 400 із повідомленням про помилку валідації.

## Індивідуальне завдання

Номер у списку групи: **17**.

Розрахунок індивідуального варіанта:

```text
V = (N % 3) + 1
V = (17 % 3) + 1
V = 2 + 1
V = 3
```

Обраний варіант: **№3 — Account**.

Відповідно до індивідуального завдання реалізовано сутність `Account` із такими атрибутами:

- `id`
- `user_id`
- `balance`

Реалізовано такі бізнес-операції:

1. Автоматичне створення рахунку під час реєстрації користувача.
2. Поповнення рахунку через `POST /account/{user_id}/deposit`.
3. Перегляд балансу через `GET /account/{user_id}`.
4. Автоматичне списання суми витрати з балансу під час створення запису.
5. Перевірка достатності коштів перед створенням витрати.
6. Відхилення операції, якщо коштів недостатньо.

Якщо баланс рахунку менший за суму витрати, API повертає HTTP 400 з помилкою `insufficient_funds`.

## Тестування API

Для документування та ручного тестування запитів використовується Bruno.

Колекція запитів зберігається в директорії `bruno_collection/`.

Для автоматизованого тестування використовується Pytest.

Тестова конфігурація створює окрему базу даних і не змінює робочу базу застосунку.

Для запуску тестів локально:

```powershell
.\.venv\Scripts\python.exe -m pytest -v
```

Реалізовані перевірки:

- працездатність застосунку (`/healthz/live`);
- готовність бази даних (`/healthz/ready`);
- заморожений час за допомогою Freezegun;
- реєстрація та вхід користувача;
- перевірка неправильного пароля;
- доступ до захищених маршрутів;
- доступ користувача до власного профілю;
- заборона доступу до чужого профілю;
- обмеження доступу до списку користувачів;
- права аудитора на читання;
- заборона аудитору виконувати операції запису;
- права адміністратора.

## Автоматизація перевірок (CI Pipeline)

Для автоматизації перевірок використовується GitHub Actions.

CI Pipeline запускається після надсилання змін (`push`) або створення запиту на злиття (`pull_request`) у гілки `main` та `master`.

CI Pipeline включає:

1. Отримання вихідного коду репозиторію.
2. Налаштування Python 3.13.
3. Встановлення залежностей із `requirements.txt`.
4. Запуск статичного аналізу коду за допомогою Ruff.
5. Запуск автоматизованих тестів Pytest.
6. Використання PostgreSQL 16 як сервісу для тестування.
7. Збирання Docker-образу.
8. Перевірку конфігурації Docker Compose.
